# Overlayable 층별 그래프 편집: 에이전트 작업 참고

작성일: 2026-09-17. 독자: 이후 같은 작업을 수행할 에이전트.
출처: HongGwart 작업 공간에서 작성한 C동 5층 작업 기록. Overlayable 저장소에서도 참조할 수 있도록 수록했다.
사용자가 문서를 읽거나 작업 절차를 다시 설명하지 않아도 이어서 작업하기 위한 기록이다.

## 적용 범위와 근거

사용자가 이미 열어둔 크롬의 **geojson.io + Overlayable** 화면에서
실내 도면에 노드와 간선을 배치하는 작업에 적용한다.
이 문서 자체가 새로운 레이어 편집이나 다른 층 수정에 대한 허가는 아니다.
현재 요청의 대상 층을 확인하고 그 범위에서 실행한다.

사례 요청은 “T동에 찍어둔 노드·간선과 마찬가지로, 현재 열린 C동 5층에도 찍어 달라”였다.
T동 5층을 읽어서 형식을 파악한 뒤 C동 5층만 편집했다.
브라우저 화면에서 읽고 썼으며 백엔드 API를 직접 호출하거나 프로젝트 소스를 수정하지 않았다.

참조 위치:

- 도면: 별도 HongGwart 작업 공간의 `Floor Plan/C_5.png`, `Floor Plan/T_5.png`.
- 이 절의 도면·백엔드 경로는 HongGwart 작업 공간 기준이다. 이 문서가 있는 Overlayable 저장소에는
  해당 도면이나 백엔드 소스가 포함되어 있지 않으므로, 현재 환경에서 HongGwart 위치를 확인한다.
- 편집 화면: `https://geojson.io/`, Overlayable의 `HONGGWART 공유 레이어` 패널.
- 당시 연결 서버: `http://honggwart.duckdns.org:8081`.
  현재 연결 주소는 반드시 패널에서 확인한다. 인증 정보는 이 문서에 저장하지 않는다.
- 데이터 의미 확인용 소스:
  `Backend/src/main/java/com/honggwart/map/domain/layer/application/LayerWorkspaceService.java`
  및 같은 `layer` 디렉터리 아래 `dto/LayerDtos.java`.

## 먼저 확인할 것

1. 현재 제공된 브라우저 도구의 지침을 읽고, 사용자가 지정한 크롬의 기존 탭을 선택한다.
   당시 탭 ID, 변수 바인딩, 접근성 요소 번호는 재사용하지 않는다.
2. 선택 레이어의 건물·층, 표시 이미지 이름, 저장 상태와 저장 버전(`revision`)을 확인한다.
   처음 C동 5층은 `C_5.png`와 빈 지형지물 모음(`FeatureCollection`), 저장 버전 11이었다.
3. 기존 데이터가 있으면 편집 전 전체 GeoJSON을 확보한다.
   전체 JSON 입력은 추가 명령이 아니라 **레이어 전체 스냅샷 교체**라는 점에 유의한다.
4. 참조 층 하나를 열고 전체 GeoJSON과 실제 배치를 읽는다.
   기존 층의 이미지나 데이터를 변경하지 않고 대상 층으로 돌아온다.
5. 대상 도면의 기존 지리적 정렬을 존중한다.
   이번 작업은 사용자가 맞춰둔 도면 위치를 기준으로 했으며 실제 건물 좌표를 측량하지 않았다.

## T동에서 확인하고 따른 모델링 규칙

| 대상 | 노드 유형(`nodeType`) | 검색 가능 여부(`searchable`) | 이름·호실 |
| --- | --- | --- | --- |
| 호실 출입구 | POI | true | `C501`, roomNumber `501` |
| 같은 호실의 별도 출입구 | POI | true | 같은 이름·호실 번호, 서로 다른 UUID·좌표 |
| 일반 복도 연결점·꺾임 | WAYPOINT | false | `C5 … 연결점`, roomNumber null |
| 분기·교차점 | JUNCTION | false | `C5 … 교차점`, roomNumber null |
| 계단·엘리베이터 | VERTICAL_LINK | false | `C5 … 계단` / `C5 … 엘베`, roomNumber null |
| 화장실 | POI | true | 남/녀 및 위치 구분, roomNumber null |

T동의 호실 POI는 문 위치에 대응하는 **복도 중심선상의 지점**으로 배치되어 있었다.
C동도 이 방식을 적용했다. 방 중심을 찍는 방식이 아니다.
문이 여러 개인 방은 출입구별로 노드를 만들되, 도면의 문 표시를 각각 확인한다.
서로 마주 보는 문이나 가까운 문은 좌표가 같아지지 않도록 위치를 세밀하게 구분한다.
작은 임의 간격을 일반 규칙으로 고정하지 말고 도면의 실제 출입구를 우선한다.

복도는 `CORRIDOR`, `indoor: true`, `bidirectional: true`로 연결했다.
방이나 벽을 가로지르는 지름길을 만들지 않는다.
계단·엘리베이터는 접근 가능한 홀·통로를 거쳐 연결한다.
특히 C동 중앙 계단은 주복도에서 벽을 가로질러 직결하지 않고 홀을 돌아 접근했다.

**VERTICAL_LINK 노드를 만드는 것과 층간 간선을 만드는 것은 별개다.**
이번 작업에서는 C동 5층 내부 연결만 생성했다.
다른 층과의 계단(`STAIR`)·엘리베이터(`ELEVATOR`) 연결은 상대 층 노드가 확인되는 별도 작업이다.

## 도면 판독과 화면 조작

- 전체 화면 캡처로 위치 관계를 먼저 파악한다.
- 도면 글씨가 작거나 회전되어 있으면 원본 이미지를 읽는다.
  당시 문서 구조(DOM)에 `.imgovl-overlay-img`가 있었고,
  그 `src`는 PNG 이미지 데이터를 포함한 주소(`data:` URL)였다.
  이 이미지를 그대로 표시해 회전 전 도면의 호실·문·벽을 판독했다.
  원본 크기는 2056 × 2738이었다. 다른 이미지에는 재사용하지 않는다.
- 이미지가 별도로 캡슐화된 문서 구조(섀도 DOM) 안에 있을 수 있다.
  일반 스냅샷에 확장 패널이 안 보여도 접근성 트리에는 보일 수 있다.
  원본 이미지와 표시 스타일을 읽을 때는 현재 도구가 허용하는 읽기 전용 DOM 조회를 사용한다.
- 도면 판독 중 투명도를 100%로 올렸지만, 이 상태에서는 아래의 노드·선이 가려진다.
  최종 시각 검토 때는 원래 값인 59%로 되돌렸다.
- 이미지 크기·회전 조절과 지도 줌·이동을 혼동하지 않는다.
  지도에 고정된 이미지는 지도 줌에 따라 패널의 확대/축소 값도 달라진다.
- `⌘`를 누르면 Overlayable이 이미지 조작 모드가 된다.
  단축키 후 패널이 `이미지 모드`에 머물면 보조 키가 해제됐는지 확인한다.
  당시 `pressKey('super')`와 `Escape` 후 `웹 모드`로 돌아온 것을 확인했다.
  이미지 모드인 채로 지도를 드래그하지 않는다.
- 지도 드래그에는 관성이 있었다. 동작 직후 캡처와 최종 위치가 달랐다.
  줌·이동 후 화면과 DOM 변환값이 안정된 상태에서만 좌표를 채집한다.
- 줌이나 드래그를 빠르게 연속 실행하기보다 한 번 실행한 뒤 상태를 확인한다.
  실제 사례에서는 저장 후 지도 URL의 시점을 지정해 화면을 다시 잡았다.
  페이지 재로드는 편집 중 입력을 잃을 수 있으므로 저장 상태를 먼저 확인한다.

## 좌표를 만든 방법

모든 지점을 하나씩 마우스로 찍지 않았다.
**원본 도면의 픽셀 좌표 → 현재 화면 좌표 → 지리 좌표**로 변환한 뒤,
GeoJSON 편집기에 노드와 선을 함께 입력했다.

1. 원본 도면에서 복도 중심선, 문, 분기, 계단·엘리베이터 접근 지점의 `(u, v)`를 읽는다.
2. 현재 DOM에서 이미지 원본 크기 `(W, H)`, 표시 크기 `(w, h)`,
   화면상의 이미지 중심 `(cx, cy)`, 회전각 `θ`를 읽는다.
   당시 `.imgovl-frame`의 인라인 스타일과 이미지 경계 사각형을 사용했다.
3. 현재 화면 좌표는 아래 식으로 구한다. 화면의 y축은 아래가 양수다.

   ```text
   dx = (u - W/2) * w/W
   dy = (v - H/2) * h/H
   sx = cx + dx*cos(θ) - dy*sin(θ)
   sy = cy + dx*sin(θ) + dy*cos(θ)
   ```

   이 식은 당시처럼 평면 이미지가 중심 기준으로 크기 조절·회전된 경우다.
   다른 CSS 변환·원근이 있으면 그대로 적용하지 않는다.

4. 실제 필요한 연결점 하나를 화면에서 찍고, 클릭 화면 좌표와 생성된 점(`Point`)의 경위도를 읽어
   기준점으로 삼는다. 임시 점만 만들었다면 불필요하게 남겨두지 않는다.
   당시 첫 점은 최종 `C5 북측 홀 연결점`으로 이름과 좌표를 조정해 재사용했다.
5. 당시 지도는 북쪽이 위인 평면 웹 메르카토르 투영이었다.
   전체 지도 픽셀 크기는 `512 * 2**zoom`으로 계산했다.
   기준점 `(sx0, sy0)`의 경위도가 `(lng0, lat0)`일 때:

   ```js
   const world = 512 * 2 ** zoom;
   const rad = lat0 * Math.PI / 180;
   const my0 = (1 - Math.log(Math.tan(rad) + 1 / Math.cos(rad)) / Math.PI) / 2;
   const lng = lng0 + (sx - sx0) * 360 / world;
   const my = my0 + (sy - sy0) / world;
   const lat = Math.atan(Math.sinh(Math.PI * (1 - 2 * my))) * 180 / Math.PI;
   ```

   타일 크기 512픽셀, 줌 정밀도, CSS 픽셀 기준,
   지도 회전각(`bearing`)과 기울기(`pitch`)가 모두 0이라는 조건을 확인한다.
   좌표 순서는 GeoJSON의 **[경도, 위도]**다. 당시 소수점 7자리로 입력했다.
   URL의 반올림된 줌만으로 정밀도를 보장하지 않는다.
   다음 작업에서는 충분히 떨어진 기준점 둘 이상으로 변환 오차를 확인하는 것이 좋다.
   이는 이번 작업의 개선 제안이며 당시 실행한 검증으로 표현하지 않는다.
6. 원본 도면의 위쪽이 지리적 북쪽이라고 가정하지 않는다.
   C동 도면은 약 -178.1° 회전되어 있었으므로 동/서 및 북측 명칭을 실제 지도 기준으로 정했다.
7. Point 좌표와 이를 참조하는 LineString 꼭짓점 좌표는 같은 계산 결과를 재사용한다.

당시 계산값의 예시는 다음과 같다. **재현 기록일 뿐 현재 좌표 계산에 복사하지 않는다.**

```text
원본 이미지: 2056 × 2738
표시 이미지: 688.16 × 916.44 CSS px
이미지 중심: (1227.12, 646.46)
회전: -178.09°
지도 줌: 19
기준 클릭: (1327, 340)
기준 경위도: (126.9261635, 37.5497924)
```

## GeoJSON 데이터 형식

점(`Point`) 예시의 꺾쇠 괄호 값은 설명용 자리표시자다. 실제 입력에는 유효한 UUID·좌표를 넣는다.

```json
{
  "type": "Feature",
  "id": "<노드 UUID>",
  "properties": {
    "overlayable": {"kind": "node", "editorId": "<동일한 노드 UUID>"},
    "name": "C501",
    "nodeType": "POI",
    "searchable": true,
    "roomNumber": "501",
    "data": {"buildingCode": "C", "floorCode": "5"}
  },
  "geometry": {"type": "Point", "coordinates": [126.0, 37.0]}
}
```

- 신규 노드에는 새로운 UUID를 만든다. 기존 노드는 `id`와 `overlayable.editorId`를 유지한다.
- 신규 `nodeId`는 임의로 생성하지 않는다. 백엔드 저장 후 숫자 ID가 반환된다.
- 기존 노드의 `nodeId` 및 추가 메타데이터는 보존한다.
- T동에는 과거 시트 가져오기로 기록된 `sourceSheet`, `sourceRow`, `sourceName`이 있었다.
  새 도면 판독 데이터에 그 출처를 복사하거나 꾸며내지 않는다.

선(`LineString`)의 속성(`properties`)은 아래 구조를 사용한다.

```json
{
  "overlayable": {
    "kind": "edge-chain",
    "featureId": "<선 UUID>",
    "vertexNodeIds": ["<노드 A의 UUID>", "<노드 B의 UUID>"],
    "segmentEdgeIds": []
  },
  "edgeType": "CORRIDOR",
  "indoor": true,
  "bidirectional": true,
  "data": {}
}
```

선 지형지물의 `id`는 `featureId`와 같은 UUID다.
`vertexNodeIds`에는 데이터베이스의 숫자 `nodeId`가 아니라 **노드의 편집용 UUID(`editorId`)**를 넣는다.
배열 순서와 길이를 `geometry.coordinates`와 일치시킨다.
신규 `segmentEdgeIds`는 빈 배열로 저장하고, 반환된 숫자 ID를 확인한다.

문서 작성 시 백엔드 `saveSnapshot`에서 확인한 동작:

- 점과 선을 받고, 선의 인접 꼭짓점마다 데이터베이스 간선(`Edge`)을 생성한다.
- 기존 노드는 편집용 UUID로 찾는다.
- 스냅샷에서 빠진 기존 노드는 삭제 대상이 된다.
- 해당 레이어의 간선은 저장할 때 다시 생성한다. 숫자 `segmentEdgeIds`는 고정값이 아니다.
- `expectedRevision`으로 저장 충돌을 감지한다.
- 노드의 건물·층은 선택한 레이어에서 결정한다.
  `properties.data`에 층 정보를 적는 것만으로 잘못 선택한 레이어를 보완할 수 없다.

기존 데이터가 있는 층에서는 최신 스냅샷에 변경을 통합한다.
충돌이 발생하면 다른 변경을 다시 읽고 통합한다. 오래된 전체 JSON을 그대로 덮어쓰지 않는다.

## 화면 반영과 저장

1. 현재 화면에서 확인한 JSON 에디터를 사용한다.
   이번 CodeMirror 에디터는 `.cm-content`였으며
   `.fill(JSON.stringify(collection, null, 2))`로 입력했다.
   브라우저의 비공개 상태나 확장 기능 내부 저장소를 직접 수정하지 않았다.
2. 확장 패널이 JSON 영역을 가리면 일시적으로 접는다.
3. 입력 직후 목록에 이전 데이터가 보일 수 있다. 포커스를 옮기고 화면 상태를 확인한다.
   자동 적용과 저장에 지연이 있었다.
4. 모든 항목이 이름 없이 `Point`로 표시되면 이름 표시 속성(`Label property`)을 `name`으로 설정한다.
   이름이 삭제됐다고 판단해 노드를 다시 만들지 않는다.
5. 상태가 `저장 중…`에서 `저장됨` 또는 `동기화됨`으로 바뀌고 저장 버전이 갱신되는지 확인한다.
6. JSON의 복사(`Copy`) 버튼으로 저장 후 전체 데이터를 읽어 검증한다.
   CodeMirror의 DOM 텍스트는 가상화 때문에 일부만 보일 수 있다.
   `innerText()`가 전체 JSON이라고 가정하지 않는다.
7. 복사 후 화면 상태를 확인한 다음 클립보드를 읽는다.
   최초 시도에서는 즉시 읽은 값이 비어 있었다. 빈 문자열을 JSON.parse하지 않는다.
   복사한 지형지물 모음과 대상 층의 이름을 확인해 이전 클립보드와 혼동하지 않는다.
8. `⌘A`가 에디터 텍스트 대신 모든 지형지물을 선택하기도 했다.
   전체 입력에는 에디터의 `.fill()`, 전체 읽기에는 복사 버튼을 사용하는 편이 명확했다.

## 완료 검증

- 대상 레이어·건물·층이 정확한지 확인한다.
- 기존 데이터와 노드 ID를 의도치 않게 누락하지 않았는지 확인한다.
- 점의 UUID가 고유하고 이름·유형·검색 가능 여부·호실 번호가 저장됐는지 확인한다.
- 모든 `vertexNodeIds`가 실제 점을 참조하는지 확인한다.
- 선 꼭짓점과 참조 Point의 좌표가 일치하는지 확인한다.
- 고립 노드, 의도치 않은 길이 0의 구간과 중복 구간을 확인한다.
- 양방향 인접 리스트를 만들고 너비 우선 탐색이나 깊이 우선 탐색으로 연결 성분을 확인한다.
  실제로 통로가 연결된 층에만 전체 연결을 기대한다. 분리 구역을 억지로 잇지 않는다.
- 저장 후 JSON에 서버가 발급한 `nodeId`와 `segmentEdgeIds`가 있고 동기화가 끝났는지 확인한다.
- 도면 위에서 선이 복도를 따르고 계단·엘리베이터 접근선이 벽을 통과하지 않는지 확인한다.
- 전체 화면과 읽을 수 있는 확대 화면을 함께 사용한다.
  가까운 노드의 라벨 겹침과 실제 좌표 중복은 구분한다.
- 사용자가 결과를 볼 수 있도록 대상 층을 열고 이미지 조작 모드에서 웹 모드로 돌아온다.

**선(`LineString`) 개수와 데이터베이스 간선 개수는 다르다.**
꼭짓점이 n개인 선은 n−1개 구간을 만든다.
사용자에게 간선 수를 보고할 때는 LineString 수가 아니라 실제 구간 수를 사용한다.
