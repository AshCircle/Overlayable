# Overlayable 층별 그래프 편집: 에이전트 작업 지침

<!-- shared-guidance:start -->
현행 지침 개정일: 2026-10-13. 독자: geojson.io + Overlayable에서 노드·간선을 편집하는 에이전트.
목표는 **한 번의 요청 안에서 배치 → 검수 → 자체 보정 → 저장값 재검증까지 수행하는 것**이다.
한 번의 입력이나 저장 성공만으로 작업을 완료하지 않는다.

## 1. 현행 기본 규칙

- 현재 사용자의 명시적 요청, 현재 도면·레이어 데이터, 현재 도구 지침이 우선한다. 사용자가 특정 기존 방식과 같게 작업하라고 했다면 그 요청을 따른다.
- **신규 배치의 기본은 복도 골격과 출입구 POI의 분리**다. 복도 중심선·코너·분기를 먼저 정하고 실제 문 위치의 POI를 짧은 접근 간선으로 연결한다. 기존 그래프의 구조 전환은 별도 요청 범위다.
- 요청 대상 층을 편집한다. 다른 층은 대응 구조 확인을 위해 읽을 수 있지만, 이 문서만으로 다른 층 수정·도면 이동·기존 그래프 이전·층간 연결 생성까지 허용되지는 않는다.
- 확인되지 않는 출입구·통행 가능 여부·실제 소속은 추측하지 않는다. 확인된 구간을 완성하고 **보류 목록에 대상·이유·필요한 근거**를 남긴다. 보류가 있으면 전체 완료라고 표현하지 않는다. 사용자가 이미 설명한 동일 대상은 다시 묻지 않는다.
- 현재 소유 레이어와 실제 건물·층을 구분한다. 실제 소속은 Point의 `properties.location`에서 확인하며, 노드 이름·호실 번호·`properties.data`에서 추정하지 않는다.
- 좌표·revision·화면 요소 번호·기준층·기존 개수는 과거 기록에서 복사하지 않는다. 아래 C5 부록의 직렬형 POI 배치와 구형 JSON은 당시 기록이며 현행 기본값이 아니다.

현행 조작은 [Overlayable 사용자 가이드][user-guide], 저장 계약은 [Backend 편집 프로토콜 v2][workspace-v2]를 함께 확인한다. 이 문서는 API·코드·스키마 변경 지시가 아니다.

## 2. 작업 순서

### 2.1 대상·기존 데이터·근거 확보

1. 현재 브라우저 도구 지침을 읽고 사용자가 지정한 기존 탭을 선택한다. 연결 서버, 레이어 ID·이름, 이미지, 실제 소속 목록, 저장 상태와 최신 revision을 확인한다.
2. 전체 소유 GeoJSON, 이미지 정렬, 필요한 참조 정보와 관련 revision을 확보한다. 기존 데이터가 있는 상태에서 전체 JSON 입력은 **추가가 아닌 스냅샷 교체**다. 최신 데이터에 변경을 통합한다.
3. 원본 도면과 전체 화면을 읽고 복도, 벽, 문, 홀, 계단·승강기 접근부, 혼합 건물 경계, 야외 구간을 구분한다. 작은 글씨와 문 기호는 원본 확대 화면으로 확인한다. 없는 호실 번호를 연속 번호로 채우지 않는다.
4. 사용자 확인 사항을 `대상 건물·층·구간 / 확인 내용 / 출처 대화·날짜 / 적용 범위`로 기록한다. 과거 확인이 현재 대상과 같은 공간인지 대조한다. 사실, 도면 판독, 미확정 추정을 구분한다.
5. 도면 정렬을 보존한다. 지도 배경의 건물 윤곽을 정답으로 가정하지 않는다. 도면의 정렬 오류가 의심되면 그래프 좌표로 억지 보상하지 않고 해당 구간의 한계·보류 사유를 남긴다. 정렬 변경이 이미 요청 범위에 포함돼 있으면 먼저 정렬을 확정하고 좌표 변환을 새로 검증한다.

작업 근거에는 최신 백업, 원본 이미지와 변환 정보, 중심선·대응점, 검증 결과, 보류 목록을 남긴다. 인증 정보는 기록하지 않는다. 임시 백업이나 과거 산출물을 최신 서버 데이터로 취급하지 않는다.

### 2.2 복도 골격과 층간 대응 구간 결정

1. 양쪽 벽과 실제 통행 공간을 기준으로 방향이 일정한 구간별 중심선을 정한다. 복도 폭 변화, 실제 꺾임, 분기, 장애물 우회는 따로 표시한다. 기존 노드가 일직선이라는 이유만으로 그것을 중심선으로 채택하지 않는다.
2. 같은 건물의 검증된 공통 기준이 있으면 최신 도면과 대조해 사용한다. 없으면 대응 구조가 있는 다른 층을 읽어 비교한다. 참조층이 없거나 대응 여부가 불분명하면 해당 층의 확실한 구조만 배치하고 층간 비교 한계를 기록한다.
3. 도면들을 공통 좌표계로 겹쳐 벽·복도·코어의 공간 관계를 확인한다. **동일한 물리 위치와 동일한 노드 의미**가 확인된 구간만 같은 중심선·코너·분기 좌표를 사용한다. 참조층에 보정이 필요하더라도 요청 밖의 층을 자동 수정하지 않는다.
4. 층별 문 위치와 달라진 구조는 독립적으로 배치한다. 같은 계단실이어도 층별 계단참·출입 방향이 다를 수 있다. 이름이나 시설 아이콘 중심이 같다는 이유로 같은 지점이라고 판단하지 않는다.
5. 직선 복도 연결점은 해당 축에 투영해 공선으로 배치한다. 실제 직각 코너만 직교시킨다. 방향·각도 계산은 도면 좌표나 적절한 투영 좌표에서 하며 경위도 값을 그대로 평면 좌표로 사용하지 않는다. R동 같은 실제 경사축과 꺾임을 화면 수평·수직에 맞춰 펴지 않는다.

호실별 점을 차례로 연결해 복도 골격을 만들지 않는다. 평행·직각 검사와 함께 **벽 기준 중심선으로부터의 이탈**을 별도로 검사한다. 열린 홀에서는 확인된 통행 가능 영역 안에 명시적인 연결 경로를 정하고, 양쪽 벽이 없는 곳에 가상의 복도 중선을 강요하지 않는다.

### 2.3 출입구·시설 연결

| 대상 | 유형·검색 | 배치 기준 |
| --- | --- | --- |
| 호실 출입구 | `POI`, `searchable: true` | 실제 문 위치. 호실의 방 중심이 아님. 문마다 별도 POI, 같은 이름·호실 번호 가능 |
| 일반 복도 연결점·꺾임 | `WAYPOINT`, `false` | 결정한 중심선·실제 코너 |
| 분기·교차점 | `JUNCTION`, `false` | 복도와 접근 간선이 공유하는 실제 접점 |
| 계단·엘리베이터 접근점 | `VERTICAL_LINK`, `false` | 통행 가능한 계단참·문·홀 접근 위치. 아이콘 중심만 보고 결정하지 않음 |
| 화장실 | `POI`, `true` | 확인된 출입구. 성별·위치 구분, 호실 번호가 없으면 `roomNumber: null` |

- 문 POI에서 복도 중심선으로 짧은 접근 간선을 만든다. 수직 투영이 실제 통행 경로 안에 있으면 사용하고, 벽·문 방향·홀 구조 때문에 돌아가야 하면 필요한 꺾임점을 둔다.
- 마주 보는 두 문은 서로 다른 POI를 유지하면서 하나의 복도 분기점을 공유할 수 있다. 가까운 문이나 라벨 겹침 때문에 임의 간격·지그재그를 추가하지 않는다.
- 독립 POI와 복도 연결점은 서로 다른 편집 UUID와 명시적 `vertexRefs`로 구분한다. 자동 근접 연결을 피하려고 좌표를 왜곡하지 않는다. 저장 후 두 역할의 ID가 의도대로 분리됐는지 확인한다.
- 일반 실내 복도·접근 간선은 실제 조건에 맞춰 `CORRIDOR`, `indoor: true`, `bidirectional: true`로 설정한다. 일방통행 등 확인된 예외는 실제 조건을 따른다.
- 방 내부를 공용 통로로 가로지르거나 벽을 통과하는 지름길을 만들지 않는다. 문이 보이지 않는다는 이유로 임의의 문을 만들지 않는다. 열린 구역은 도면 또는 사용자 확인 근거가 있을 때 출입문 없이 접근 경로를 구성할 수 있다.
- 다른 층의 노드는 같은 좌표여도 별도 ID로 유지한다. `VERTICAL_LINK` 배치와 층간 간선 생성은 별개이며, 층간 연결은 요청 범위와 실제 대응 관계가 확인된 경우에만 수행한다.
- 기존 그래프를 좌표 보정하는 작업에서는 ID·접속 순서·연결 관계를 유지한다. 신규 기본값을 이유로 기존 직렬형을 가지형으로 전환하지 않는다. 중심선 정렬 시 기존 노드가 겹치거나 순서가 뒤집히면 임의 병합 대신 필요한 구조 변경을 보류·보고한다.

### 2.4 좌표 변환 검증

1. 가능하면 원본 도면 픽셀 좌표로 배치 근거를 관리한다. 현재 이미지 크기·화면 변환·회전, 정확한 지도 줌·bearing·pitch를 확인한다. 도구가 허용하는 DOM 읽기나 현재 제공된 변환 정보만 사용한다.
2. 서로 멀리 떨어진 기준점으로 변환을 계산·확인하고, **계산에 사용하지 않은 별도 지점**에서 잔차를 검사한다. 평면 유사 변환이라면 최소 두 계산 기준점과 다른 방향의 독립 검사점 하나를 확보한다. 다른 변환 모델에는 충분한 추가 기준점을 확보한다.
3. 화면 클릭 기준점이 필요하면 실제로 필요한 노드를 재사용하고, 임시 점·선이 최종 그래프에 남지 않게 한다. 관성 이동과 변환값이 안정된 뒤에 화면 좌표를 채집한다.
4. 지도 줌·이동, 창·패널 크기 변화, 이미지 변형 뒤에는 기존 화면 변환값을 폐기하고 다시 구한다. 이미지 정렬 변화가 없다면 원본 픽셀상의 배치 근거는 유지할 수 있다.
5. GeoJSON 좌표는 `[경도, 위도]` 순서다. Point와 이를 참조하는 모든 LineString 꼭짓점은 동일한 계산 결과를 재사용한다. 부록의 `512 * 2**zoom` 계산은 그 투영·픽셀·bearing/pitch 조건이 현재도 성립하는지 확인한 뒤에만 참고한다.

검사점 오차가 설명되지 않으면 근삿값으로 대량 입력하지 않는다. 새 기준점을 확보하거나 변환을 바로잡고 재검사한다. 해결되지 않으면 해당 배치를 보류한다. 변환 잔차와 도면 자체의 판독·정렬 오차는 다른 항목으로 기록한다.

### 2.5 v2 형식과 저장

#### 실제 소속·참조·비용

- `FLOOR_PLAN` 소유 레이어에 여러 건물·층이 있을 수 있다. 새 노드와 자동 생성 꼭짓점의 실제 소속을 먼저 선택하고, 기본 소속을 바꾸기 전의 신규 입력은 이전 소속으로 확정·저장한다.
- 소속은 `properties.location = {buildingNodeId, floor, floorOrder}`다. 현재 등록된 소속 목록을 사용한다. `properties.data`의 건물·층 표기만 바꿔 실제 소속을 보완하지 않는다.
- 공용 경로는 `SHARED_PATHS`로 관리한다. 지상 길과 상부 통로 등 다른 높이의 길은 별도 레이어로 유지한다. 공용 점의 `buildingNodeId: null`, `floor: "0"`, `floorOrder: 0`은 미지정 호환값이며 지상층·절대고도가 아니다.
- `edgeType`과 `indoor`는 독립적이다. 야외 계단은 `STAIR + indoor=false`, 실내 공용 통로는 `CORRIDOR + indoor=true`다.
- 로컬 꼭짓점은 `vertexRefs: [{editorId: "…"}, …]`, 외부 꼭짓점은 `{nodeId, ownerLayerId}`로 명시한다. 배열의 순서·길이는 `geometry.coordinates`와 일치시킨다. `vertexNodeIds`를 함께 유지할 때 로컬 값은 같은 순서의 편집 UUID다. 외부 노드를 로컬 UUID만으로 참조하지 않는다.
- 참조 Point와 참조 사진은 소유 GeoJSON·이미지 변형 목록 밖에 둔다. 숨기거나 보기용 투명도를 바꾸는 것은 원본 변경이 아니다. 다른 층 출입구를 복제하거나 참조 노드를 현재 레이어에서 이동하지 않는다.
- 자동 근접 연결은 같은 소유 레이어·같은 실제 소속에서만 적용된다. 사용자 가이드의 1m 근접 탐색과 약 2cm 동일 노드 좌표 판정은 **도면 배치 정확도의 허용치가 아니다**.
- 기존 노드의 `id`, `editorId`, `nodeId`, 메타데이터를 보존한다. 기존 선의 `id`·`featureId`, 순서 있는 끝점 참조, `segmentEdgeIds`, 비용 설정을 보존한다. 신규 숫자 DB ID는 서버가 발급한다.
- 좌표만 보정할 때 기존 간선 ID와 `MANUAL` 비용이 유지되는지 재조회한다. 체인 분할·역순·끝점 변경은 새 구간으로 처리될 수 있으므로 기존 `segmentEdgeIds`만 복사해 ID 보존을 보장하지 않는다. 신규 일반 거리 간선은 `AUTO`를 사용하고, 기존 수동 비용을 자동 비용으로 바꾸지 않는다.

#### 현행 GeoJSON 예시

아래는 **복도 분기점과 문 POI 사이 접근 간선 하나**의 형식 예시이며 완성된 복도 전체가 아니다. UUID·좌표·`buildingNodeId: 123`은 가상값이다. 실제 입력은 신규 UUID와 현재 등록된 실제 소속으로 구성한다. 이 예시는 GeoJSON 본문이며 snapshot 요청 전체가 아니다.

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "id": "00000000-0000-4000-8000-000000000001",
      "properties": {
        "overlayable": {"kind": "node", "editorId": "00000000-0000-4000-8000-000000000001"},
        "name": "C5 501호 앞 복도 분기점", "nodeType": "JUNCTION",
        "searchable": false, "roomNumber": null,
        "location": {"buildingNodeId": 123, "floor": "5", "floorOrder": 5}, "data": {}
      },
      "geometry": {"type": "Point", "coordinates": [126.0, 37.0]}
    },
    {
      "type": "Feature",
      "id": "00000000-0000-4000-8000-000000000002",
      "properties": {
        "overlayable": {"kind": "node", "editorId": "00000000-0000-4000-8000-000000000002"},
```

신규 `AUTO` 간선의 `weights`는 생략할 수 있으며 서버가 거리를 계산해 구간별 배열로 반환한다. 기존 `weights`는 보존한다. 신규 `MANUAL` 값은 유한한 양수이며 n개 꼭짓점에 n−1개 구간 값을 대응시킨다.

#### 반영·충돌·재조회

1. 입력 전 대상 레이어를 다시 확인한다. 현재 UI의 JSON 에디터에서 최신 전체 데이터에 변경을 통합한다. Point와 선을 별도로 움직여 동일 노드에 서로 다른 좌표를 보내지 않는다. UI에서는 한 표현을 이동하고 동기화하며, 일괄 JSON 입력에서는 공통 계산 결과를 쓴다.
2. v2 snapshot은 `protocolVersion: 2`, 최신 `expectedRevision`, `defaultLocation`, 필요한 `referenceRevisions`, 소유 `geojson`·`images`를 다룬다. 브라우저 편집에서는 확장이 이를 처리한다. JSON 에디터에 snapshot 요청 전체를 붙여 넣지 않는다.
3. 외부 연결이 있으면 참조 끝점의 소유 레이어와 들어오는 외부 간선의 소유 레이어 revision도 확인한다. 참조를 제거하는 저장에도 관련 revision이 필요하다. 외부 간선이 연결된 로컬 노드를 이동하면 관련 `AUTO` 비용·revision 갱신은 예상된 파생 변경으로 재조회하고 `MANUAL` 비용 보존을 확인한다. 409 등 충돌 시 최신값을 다시 읽어 통합하며 오래된 전체 JSON으로 덮어쓰지 않는다.
4. 저장 완료·동기화 상태와 revision 갱신을 확인한 뒤 전체 GeoJSON을 다시 읽는다. 가상화된 에디터 DOM 텍스트를 전체라고 가정하지 않는다. Copy·내보내기 등 현재의 전체 읽기 기능을 사용하고 클립보드가 빈 값이나 이전 데이터가 아닌지 확인한다.
5. 중간 꼭짓점을 삭제하면 이웃 점끼리 직결될 수 있다. 모양 정리를 위한 삭제로 벽을 통과하는 지름길을 만들지 않는다. 기존 데이터 이전이 요청 범위에 있을 때만 후보 확인 → 이전 미리보기 → 별도 실행 → 재조회 순서로 수행한다. 건물 출입구는 원소속에 남겨 참조한다.

## 3. 완료 조건과 자체 보정

아래 네 검사를 따로 수행한다. 연결 성분이 하나이거나 입력·저장 좌표가 같다는 사실로 도면 위치 검사를 대체하지 않는다.

| 검사 | 통과 조건·증거 |
| --- | --- |
| 도면 의미 | 모든 신규·변경 문과 시설의 판독 근거가 있음. 혼합 소속·열린 구역·방 내부 통과 여부를 확인했거나 보류 목록에 구분함 |
| 기하 배치 | 모든 신규·변경 구간을 원본 확대와 화면에서 검토. 중심선 이탈, 불필요한 꺾임, 잘못된 직각, 벽 관통이 없음. 대응 층 공통 구간의 중첩을 확인하거나 비교 한계를 기록함 |
| 참조·연결 | UUID·DB ID·실제 소속·로컬/외부 참조가 일치. Point와 선 좌표 일치. 의도치 않은 고립·길이 0·중복 구간이 없음. 분리된 실제 구역은 억지로 연결하지 않음 |
| 저장 무결성 | 저장 완료 후 재조회 데이터로 검사. 기존 ID·연결·수동 비용·도면 정렬 보존과 신규 서버 ID 발급 확인. 요청 밖 데이터의 의도하지 않은 누락·변경 없음 |

기하 검수는 전체 화면만 보지 말고 복도별로 순회하며 모든 신규·변경 간선을 확대 확인한다. 특히 코너, 폭 변화, 문 밀집부, 계단·승강기 접근부를 확인한다. 선분의 검은 픽셀은 문자·시설 기호일 수도 있고 흰 픽셀은 실제 통행 증거가 아닐 수 있으므로 색상 검사만으로 합격시키지 않는다.

대표 출입구 → 복도 → 계단·승강기 경로를 따라 연결과 모양을 확인한다. 층간 공통 구간은 같은 좌표계로 겹쳐 비교하되, 존재하는 층간 연결만 사용한다. 저장 그래프에서의 경로 검토, 실제 경로 API 호출, 프런트엔드 화면 검증은 구분해서 보고하며 실행하지 않은 검증을 완료로 적지 않는다.

수치 검증에는 **변환 검사점 잔차, 중심선 이탈 거리, 구간 축 각도 오차, 층간 대응점 편차**를 단위·좌표계와 함께 남긴다. 판정 허용치는 이번 작업의 저장 좌표 정밀도·반올림·관측 오차에 근거해 검수 전에 정하고, 통과를 위해 사후 완화하지 않는다. 보편적인 cm·각도 기준을 과거 사례에서 복사하지 않는다. 저장 정밀도만으로 실제 측량 정확도를 주장하지 않는다.

오류를 찾으면 같은 요청 안에서 **보정 → 저장 → 재조회 → 영향받은 구간·경로 재검사**를 수행한다. 서버 정규화 때문에 목표가 그대로 저장되지 않으면 현재 처리와 잔차를 확인한다. 과거 T동의 임시 좌표를 거치는 저장 방법을 자동 재사용하지 않는다. 도구 실패나 근거 부족으로 해결되지 않는 항목은 보류·미완료로 보고한다.

완료 보고에는 다음을 포함한다.

- 완료한 층·구간, 노드 수, 실제 간선 구간 수. n개 꼭짓점의 LineString은 n−1개 구간이며 선 Feature 수와 다르다.
- 기하 검수 결과와 자체 보정 내용, 층간 비교 대상·결과 또는 한계.
- 저장값 재검증 결과, 저장 revision과 백업·검증 자료 위치.
- 보류 목록과 필요한 근거. 보류가 있으면 “확인된 구간 완료 / 나머지 보류”로 구분.

대상 층을 열어 두고 이미지 조작 키가 해제된 웹 모드인지 확인한다. 검수를 위해 바꾼 보기 설정은 복원하되 원래 이미지 정렬을 변경하지 않는다.

### 적용 범위와 근거

사용자가 이미 열어둔 크롬의 **geojson.io + Overlayable** 화면에서
실내 도면에 노드와 간선을 배치하는 작업에 적용한다.
이 문서 자체가 새로운 레이어 편집이나 다른 층 수정에 대한 허가는 아니다.
현재 요청의 대상 층을 확인하고 그 범위에서 실행한다.

사례 요청은 “T동에 찍어둔 노드·간선과 마찬가지로, 현재 열린 C동 5층에도 찍어 달라”였다.
T동 5층을 읽어서 형식을 파악한 뒤 C동 5층만 편집했다.
브라우저 화면에서 읽고 썼으며 백엔드 API를 직접 호출하거나 프로젝트 소스를 수정하지 않았다.

참조 위치:

- 도면: 별도 HongGwart 작업 공간의 `Floor Plan/C_5.png`, `Floor Plan/T_5.png`.
- 이 절의 도면·백엔드 경로는 HongGwart 작업 공간 기준이다. 이 문서가 있는 Overlayable 저장소에는
  해당 도면이나 백엔드 소스가 포함되어 있지 않으므로, 현재 환경에서 HongGwart 위치를 확인한다.
- 편집 화면: `https://geojson.io/`, Overlayable의 `HONGGWART 공유 레이어` 패널.
- 당시 연결 서버: `http://honggwart.duckdns.org:8081`.
  현재 연결 주소는 반드시 패널에서 확인한다. 인증 정보는 이 문서에 저장하지 않는다.
- 데이터 의미 확인용 소스:
  `Backend/src/main/java/com/honggwart/map/domain/layer/application/LayerWorkspaceService.java`
  및 같은 `layer` 디렉터리 아래 `dto/LayerDtos.java`.

### 먼저 확인할 것

1. 현재 제공된 브라우저 도구의 지침을 읽고, 사용자가 지정한 크롬의 기존 탭을 선택한다.
   당시 탭 ID, 변수 바인딩, 접근성 요소 번호는 재사용하지 않는다.
2. 선택 레이어의 건물·층, 표시 이미지 이름, 저장 상태와 저장 버전(`revision`)을 확인한다.
   처음 C동 5층은 `C_5.png`와 빈 지형지물 모음(`FeatureCollection`), 저장 버전 11이었다.
3. 기존 데이터가 있으면 편집 전 전체 GeoJSON을 확보한다.
   전체 JSON 입력은 추가 명령이 아니라 **레이어 전체 스냅샷 교체**라는 점에 유의한다.
4. 참조 층 하나를 열고 전체 GeoJSON과 실제 배치를 읽는다.
   기존 층의 이미지나 데이터를 변경하지 않고 대상 층으로 돌아온다.
5. 대상 도면의 기존 지리적 정렬을 존중한다.
   이번 작업은 사용자가 맞춰둔 도면 위치를 기준으로 했으며 실제 건물 좌표를 측량하지 않았다.

### T동에서 확인하고 따른 모델링 규칙

| 대상 | 노드 유형(`nodeType`) | 검색 가능 여부(`searchable`) | 이름·호실 |
| --- | --- | --- | --- |
| 호실 출입구 | POI | true | `C501`, roomNumber `501` |
| 같은 호실의 별도 출입구 | POI | true | 같은 이름·호실 번호, 서로 다른 UUID·좌표 |
| 일반 복도 연결점·꺾임 | WAYPOINT | false | `C5 … 연결점`, roomNumber null |
| 분기·교차점 | JUNCTION | false | `C5 … 교차점`, roomNumber null |
| 계단·엘리베이터 | VERTICAL_LINK | false | `C5 … 계단` / `C5 … 엘베`, roomNumber null |
| 화장실 | POI | true | 남/녀 및 위치 구분, roomNumber null |

T동의 호실 POI는 문 위치에 대응하는 **복도 중심선상의 지점**으로 배치되어 있었다.
C동도 이 방식을 적용했다. 방 중심을 찍는 방식이 아니다.
문이 여러 개인 방은 출입구별로 노드를 만들되, 도면의 문 표시를 각각 확인한다.
서로 마주 보는 문이나 가까운 문은 좌표가 같아지지 않도록 위치를 세밀하게 구분한다.
작은 임의 간격을 일반 규칙으로 고정하지 말고 도면의 실제 출입구를 우선한다.

복도는 `CORRIDOR`, `indoor: true`, `bidirectional: true`로 연결했다.
방이나 벽을 가로지르는 지름길을 만들지 않는다.
계단·엘리베이터는 접근 가능한 홀·통로를 거쳐 연결한다.
특히 C동 중앙 계단은 주복도에서 벽을 가로질러 직결하지 않고 홀을 돌아 접근했다.

**VERTICAL_LINK 노드를 만드는 것과 층간 간선을 만드는 것은 별개다.**
이번 작업에서는 C동 5층 내부 연결만 생성했다.
다른 층과의 계단(`STAIR`)·엘리베이터(`ELEVATOR`) 연결은 상대 층 노드가 확인되는 별도 작업이다.

### 도면 판독과 화면 조작

- 전체 화면 캡처로 위치 관계를 먼저 파악한다.
- 도면 글씨가 작거나 회전되어 있으면 원본 이미지를 읽는다.
  당시 문서 구조(DOM)에 `.imgovl-overlay-img`가 있었고,
  그 `src`는 PNG 이미지 데이터를 포함한 주소(`data:` URL)였다.
  이 이미지를 그대로 표시해 회전 전 도면의 호실·문·벽을 판독했다.
  원본 크기는 2056 × 2738이었다. 다른 이미지에는 재사용하지 않는다.
- 이미지가 별도로 캡슐화된 문서 구조(섀도 DOM) 안에 있을 수 있다.
  일반 스냅샷에 확장 패널이 안 보여도 접근성 트리에는 보일 수 있다.
  원본 이미지와 표시 스타일을 읽을 때는 현재 도구가 허용하는 읽기 전용 DOM 조회를 사용한다.
- 도면 판독 중 투명도를 100%로 올렸지만, 이 상태에서는 아래의 노드·선이 가려진다.
  최종 시각 검토 때는 원래 값인 59%로 되돌렸다.
- 이미지 크기·회전 조절과 지도 줌·이동을 혼동하지 않는다.
  지도에 고정된 이미지는 지도 줌에 따라 패널의 확대/축소 값도 달라진다.
- `⌘`를 누르면 Overlayable이 이미지 조작 모드가 된다.
  단축키 후 패널이 `이미지 모드`에 머물면 보조 키가 해제됐는지 확인한다.
  당시 `pressKey('super')`와 `Escape` 후 `웹 모드`로 돌아온 것을 확인했다.
  이미지 모드인 채로 지도를 드래그하지 않는다.
- 지도 드래그에는 관성이 있었다. 동작 직후 캡처와 최종 위치가 달랐다.
  줌·이동 후 화면과 DOM 변환값이 안정된 상태에서만 좌표를 채집한다.
- 줌이나 드래그를 빠르게 연속 실행하기보다 한 번 실행한 뒤 상태를 확인한다.
  실제 사례에서는 저장 후 지도 URL의 시점을 지정해 화면을 다시 잡았다.
  페이지 재로드는 편집 중 입력을 잃을 수 있으므로 저장 상태를 먼저 확인한다.

### 좌표를 만든 방법

모든 지점을 하나씩 마우스로 찍지 않았다.
**원본 도면의 픽셀 좌표 → 현재 화면 좌표 → 지리 좌표**로 변환한 뒤,
GeoJSON 편집기에 노드와 선을 함께 입력했다.

1. 원본 도면에서 복도 중심선, 문, 분기, 계단·엘리베이터 접근 지점의 `(u, v)`를 읽는다.
2. 현재 DOM에서 이미지 원본 크기 `(W, H)`, 표시 크기 `(w, h)`,
   화면상의 이미지 중심 `(cx, cy)`, 회전각 `θ`를 읽는다.
   당시 `.imgovl-frame`의 인라인 스타일과 이미지 경계 사각형을 사용했다.
3. 현재 화면 좌표는 아래 식으로 구한다. 화면의 y축은 아래가 양수다.

   ```text
   dx = (u - W/2) * w/W
   dy = (v - H/2) * h/H
   sx = cx + dx*cos(θ) - dy*sin(θ)
   sy = cy + dx*sin(θ) + dy*cos(θ)
   ```

   이 식은 당시처럼 평면 이미지가 중심 기준으로 크기 조절·회전된 경우다.
   다른 CSS 변환·원근이 있으면 그대로 적용하지 않는다.

4. 실제 필요한 연결점 하나를 화면에서 찍고, 클릭 화면 좌표와 생성된 점(`Point`)의 경위도를 읽어
   기준점으로 삼는다. 임시 점만 만들었다면 불필요하게 남겨두지 않는다.
   당시 첫 점은 최종 `C5 북측 홀 연결점`으로 이름과 좌표를 조정해 재사용했다.
5. 당시 지도는 북쪽이 위인 평면 웹 메르카토르 투영이었다.
   전체 지도 픽셀 크기는 `512 * 2**zoom`으로 계산했다.
   기준점 `(sx0, sy0)`의 경위도가 `(lng0, lat0)`일 때:

   ```js
   const world = 512 * 2 ** zoom;
   const rad = lat0 * Math.PI / 180;
   const my0 = (1 - Math.log(Math.tan(rad) + 1 / Math.cos(rad)) / Math.PI) / 2;
   const lng = lng0 + (sx - sx0) * 360 / world;
   const my = my0 + (sy - sy0) / world;
   const lat = Math.atan(Math.sinh(Math.PI * (1 - 2 * my))) * 180 / Math.PI;
   ```

   타일 크기 512픽셀, 줌 정밀도, CSS 픽셀 기준,
   지도 회전각(`bearing`)과 기울기(`pitch`)가 모두 0이라는 조건을 확인한다.
   좌표 순서는 GeoJSON의 **[경도, 위도]**다. 당시 소수점 7자리로 입력했다.
   URL의 반올림된 줌만으로 정밀도를 보장하지 않는다.
   다음 작업에서는 충분히 떨어진 기준점 둘 이상으로 변환 오차를 확인하는 것이 좋다.
   이는 이번 작업의 개선 제안이며 당시 실행한 검증으로 표현하지 않는다.
6. 원본 도면의 위쪽이 지리적 북쪽이라고 가정하지 않는다.
   C동 도면은 약 -178.1° 회전되어 있었으므로 동/서 및 북측 명칭을 실제 지도 기준으로 정했다.
7. Point 좌표와 이를 참조하는 LineString 꼭짓점 좌표는 같은 계산 결과를 재사용한다.

당시 계산값의 예시는 다음과 같다. **재현 기록일 뿐 현재 좌표 계산에 복사하지 않는다.**

```text
원본 이미지: 2056 × 2738
표시 이미지: 688.16 × 916.44 CSS px
이미지 중심: (1227.12, 646.46)
회전: -178.09°
지도 줌: 19
기준 클릭: (1327, 340)
기준 경위도: (126.9261635, 37.5497924)
```

### GeoJSON 데이터 형식

점(`Point`) 예시의 꺾쇠 괄호 값은 설명용 자리표시자다. 실제 입력에는 유효한 UUID·좌표를 넣는다.

```json
{
  "type": "Feature",
  "id": "<노드 UUID>",
  "properties": {
    "overlayable": {"kind": "node", "editorId": "<동일한 노드 UUID>"},
    "name": "C501",
    "nodeType": "POI",
    "searchable": true,
    "roomNumber": "501",
    "data": {"buildingCode": "C", "floorCode": "5"}
  },
  "geometry": {"type": "Point", "coordinates": [126.0, 37.0]}
}
```

- 신규 노드에는 새로운 UUID를 만든다. 기존 노드는 `id`와 `overlayable.editorId`를 유지한다.
- 신규 `nodeId`는 임의로 생성하지 않는다. 백엔드 저장 후 숫자 ID가 반환된다.
- 기존 노드의 `nodeId` 및 추가 메타데이터는 보존한다.
- T동에는 과거 시트 가져오기로 기록된 `sourceSheet`, `sourceRow`, `sourceName`이 있었다.
  새 도면 판독 데이터에 그 출처를 복사하거나 꾸며내지 않는다.

선(`LineString`)의 속성(`properties`)은 아래 구조를 사용한다.

```json
{
  "overlayable": {
    "kind": "edge-chain",
    "featureId": "<선 UUID>",
    "vertexNodeIds": ["<노드 A의 UUID>", "<노드 B의 UUID>"],
    "segmentEdgeIds": []
  },
  "edgeType": "CORRIDOR",
  "indoor": true,
  "bidirectional": true,
  "data": {}
}
```

선 지형지물의 `id`는 `featureId`와 같은 UUID다.
`vertexNodeIds`에는 데이터베이스의 숫자 `nodeId`가 아니라 **노드의 편집용 UUID(`editorId`)**를 넣는다.
배열 순서와 길이를 `geometry.coordinates`와 일치시킨다.
신규 `segmentEdgeIds`는 빈 배열로 저장하고, 반환된 숫자 ID를 확인한다.

문서 작성 시 백엔드 `saveSnapshot`에서 확인한 동작:

- 점과 선을 받고, 선의 인접 꼭짓점마다 데이터베이스 간선(`Edge`)을 생성한다.
- 기존 노드는 편집용 UUID로 찾는다.
- 스냅샷에서 빠진 기존 노드는 삭제 대상이 된다.
- 해당 레이어의 간선은 저장할 때 다시 생성한다. 숫자 `segmentEdgeIds`는 고정값이 아니다.
- `expectedRevision`으로 저장 충돌을 감지한다.
- 노드의 건물·층은 선택한 레이어에서 결정한다.
  `properties.data`에 층 정보를 적는 것만으로 잘못 선택한 레이어를 보완할 수 없다.

기존 데이터가 있는 층에서는 최신 스냅샷에 변경을 통합한다.
충돌이 발생하면 다른 변경을 다시 읽고 통합한다. 오래된 전체 JSON을 그대로 덮어쓰지 않는다.

### 화면 반영과 저장

1. 현재 화면에서 확인한 JSON 에디터를 사용한다.
   이번 CodeMirror 에디터는 `.cm-content`였으며
   `.fill(JSON.stringify(collection, null, 2))`로 입력했다.
   브라우저의 비공개 상태나 확장 기능 내부 저장소를 직접 수정하지 않았다.
2. 확장 패널이 JSON 영역을 가리면 일시적으로 접는다.
3. 입력 직후 목록에 이전 데이터가 보일 수 있다. 포커스를 옮기고 화면 상태를 확인한다.
   자동 적용과 저장에 지연이 있었다.
4. 모든 항목이 이름 없이 `Point`로 표시되면 이름 표시 속성(`Label property`)을 `name`으로 설정한다.
   이름이 삭제됐다고 판단해 노드를 다시 만들지 않는다.
5. 상태가 `저장 중…`에서 `저장됨` 또는 `동기화됨`으로 바뀌고 저장 버전이 갱신되는지 확인한다.
6. JSON의 복사(`Copy`) 버튼으로 저장 후 전체 데이터를 읽어 검증한다.
   CodeMirror의 DOM 텍스트는 가상화 때문에 일부만 보일 수 있다.
   `innerText()`가 전체 JSON이라고 가정하지 않는다.
7. 복사 후 화면 상태를 확인한 다음 클립보드를 읽는다.
   최초 시도에서는 즉시 읽은 값이 비어 있었다. 빈 문자열을 JSON.parse하지 않는다.
   복사한 지형지물 모음과 대상 층의 이름을 확인해 이전 클립보드와 혼동하지 않는다.
8. `⌘A`가 에디터 텍스트 대신 모든 지형지물을 선택하기도 했다.
   전체 입력에는 에디터의 `.fill()`, 전체 읽기에는 복사 버튼을 사용하는 편이 명확했다.

### 완료 검증

- 대상 레이어·건물·층이 정확한지 확인한다.
- 기존 데이터와 노드 ID를 의도치 않게 누락하지 않았는지 확인한다.
- 점의 UUID가 고유하고 이름·유형·검색 가능 여부·호실 번호가 저장됐는지 확인한다.
- 모든 `vertexNodeIds`가 실제 점을 참조하는지 확인한다.
- 선 꼭짓점과 참조 Point의 좌표가 일치하는지 확인한다.
- 고립 노드, 의도치 않은 길이 0의 구간과 중복 구간을 확인한다.
- 양방향 인접 리스트를 만들고 너비 우선 탐색이나 깊이 우선 탐색으로 연결 성분을 확인한다.
  실제로 통로가 연결된 층에만 전체 연결을 기대한다. 분리 구역을 억지로 잇지 않는다.
- 저장 후 JSON에 서버가 발급한 `nodeId`와 `segmentEdgeIds`가 있고 동기화가 끝났는지 확인한다.
- 도면 위에서 선이 복도를 따르고 계단·엘리베이터 접근선이 벽을 통과하지 않는지 확인한다.
- 전체 화면과 읽을 수 있는 확대 화면을 함께 사용한다.
  가까운 노드의 라벨 겹침과 실제 좌표 중복은 구분한다.
- 사용자가 결과를 볼 수 있도록 대상 층을 열고 이미지 조작 모드에서 웹 모드로 돌아온다.

**선(`LineString`) 개수와 데이터베이스 간선 개수는 다르다.**
꼭짓점이 n개인 선은 n−1개 구간을 만든다.
사용자에게 간선 수를 보고할 때는 LineString 수가 아니라 실제 구간 수를 사용한다.
